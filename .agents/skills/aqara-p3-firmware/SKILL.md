# Aqara P3 固件

复用本项目已经实机验证的用户分区自启动方案。先判断请求是离线研究、制作候选，还是执行刷写；整理文档、运行测试和生成安装包都不构成刷机授权。已有本次刷写授权时继续执行，不重复索要确认；历史安装记录不是对另一候选的授权。

## 先确定版本与状态

- 阅读 [固件与已知行为](references/firmware.md)，核对型号、镜像哈希和当前槽位。
- 旧的 `scripts/prepare_install.py` 是 **4.0.4_0016、原 rootfs bank 1 → bank 0 的历史单分区配置**。公共双分区安装使用仓库 [`firmware/p3_firmware.py`](../../../firmware/p3_firmware.py)，按实际状态生成计划，支持分别选择 kernel/rootfs 备用槽。不要混用两种流程的计划和 expected 文件，也不要修改哈希或删除备份来绕过检查。
- 此项目历史实机已成功安装用户脚本版，之后再操作很可能处于 bank 0。重新读取实机状态，不能照搬第一次安装计划。
- 原始设备备份和生成的安装计划保留在 Git 忽略的 `analysis/` 等私有目录。公开固件仅使用 `firmware/4.0.4-user-init/` 白名单：已审查的 rootfs、裁切后的内核有效负载、用户脚本及通用元数据。设备身份、密码、factory、boot_info、分区尾部残留、历史授权和专属安装计划均不进入公开包。

## 按任务加载材料

1. **制作或复现**：阅读 [构建与离线测试](references/lab.md)。使用 `scripts/build.py`、`test_runtime.py`、`test_boot_policy.py`；需要监听测试时再运行 `test_telnetd.py`。用户启动脚本位于 `assets/post_init.sh`。
2. **准备安装或排查刷写**：阅读 [安装与恢复检查](references/install.md)。`scripts/prepare_install.py` 只生成本地可审查的安装包，绝不连接设备。它生成的 `apply.sh` 会写 Flash，只能在当前请求授权、实时状态和已验证计划相符后运行。
3. **改变启动段、固件版本或槽位**：先更新对应离线用例与验证条件，重新完整构建和测试。保持原厂应用启动，再后台运行用户脚本。不能将“增加启动入口”变成替换原厂初始化流程。
4. **公开镜像、跨版本双分区安装**：先读[公开安装指南](../../../firmware/README.md)及[验证报告](../../../firmware/4.0.4-user-init/VALIDATION.md)。使用 `test_public_bundle.py` 检查完整安装脚本；`test_boot_policy.py --paired-bundle` 检查两类目标槽。兼容条件以程序指纹为准；目前公开流程的跨版本升级证据是离线模拟，应明确区别于历史实机单分区安装。

## 关键判断

- SquashFS 的 rcS 位于压缩数据中，采用完整重建。使用原始镜像在 Linux 文件系统解包，不能拿 Windows 导出的文件目录重打包。
- `fw_update` 的退出码和 `Success` 都不足以证明成功。独立回读目标负载、boot_info、保留的内核和 rootfs，再判断是否可以重启。
- 写入派发后的连接中断只允许先读状态，不能自动重跑。已有备份不可覆盖，已占用的执行目录不可删除后重试。
- QEMU 执行原厂 MIPS 升级程序，Flash 是普通文件替身；Unicorn 执行原始选槽机器码并在跳转内核前停止。报告需区分这些测试与真实 NAND、整板启动验证。
- 不把双槽等同于自动回滚。已验证引导流程会在进入内核前清零失败次数，无法据此恢复 Linux 启动失败。
